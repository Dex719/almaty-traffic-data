# almaty-traffic-data

Сбор дорожных данных Алматы для krisha-fair-price / baǵam:
баллы Яндекса и 2ГИС, пользовательские и официальные события 2ГИС,
категориальные пробки на геометриях OSM.

## Режимы работы

- **Постоянный сервер — рекомендуемый режим:** `systemd`, SQLite/WAL на постоянном
  диске, перезапуск после падения, watchdog, внешние сигналы работоспособности,
  проверяемые резервные копии. Git для сбора не нужен.
- **GitHub Actions — best-effort fallback:** вахта 330 минут, очередь через
  `concurrency`, следующий запуск через `workflow_dispatch`, cron-страховка.
  Каждые 15 минут live-представления коммитятся в `main`, а архивные потоки
  уходят неизменяемыми сегментами в prerelease `staging`; после закрытия дня
  сегменты консолидируются в дневной архив месячного релиза `data-YYYY-MM`
  (см. «Где лежат данные»). Процесс сборщика ограничен `timeout` на 340 минут,
  чтобы зависание завершалось как *failure* шага, а не отмена джоба: тогда
  recovery artifact и преемник запускаются. GitHub может задерживать/пропускать
  schedule; гарантии 24/7 нет.

Интервалы независимы: 2ГИС-балл — 60 с, Яндекс-балл — 240 с, каждый слой событий
и карта — 300 с. При задержке пропущенные слоты не догоняются шквалом запросов.
Слои событий не блокируют успешные результаты друг друга. `Retry-After`
соблюдается; после серии ошибок включается отдельный cooldown.

## Установка и запуск

Python 3.12 или 3.13, Linux для process lock/systemd. Pillow нужен для карты.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest tests/ -q
python -m collector                                      # один цикл без git
python -m collector.shift --minutes 5                    # короткий запуск без git
python -m collector.shift --forever --data-dir /var/lib/almaty-traffic
```

Только Actions использует `--git`: флаг включает публикацию в GitHub (git для
live-представлений, Releases для архивных потоков) и требует `gh` CLI с
`GH_TOKEN`/`GH_REPO` в окружении. Локальный запуск не публикует ничего без
этого явного флага. Не запускайте два экземпляра на один каталог: файловая
блокировка предотвращает второго писателя. Не запускайте серверный экземпляр
и Actions для одной публичной ленты одновременно; при переходе отключите
workflow сбора вручную после проверки сервера.

## Данные и семантика

### Где лежат данные

| Поток | Путь | Где публикуется | Как часто |
|---|---|---|---|
| Баллы и счётчики | `data/scores/YYYY-MM.csv` | git (`main`) | каждые 15 мин |
| Реестр событий | `data/events/YYYY-MM.json` | git (`main`) | не чаще раза в час (файл ~9 МБ, перезаписывается каждые 5 мин) |
| Геометрии и их версии | `data/jam_map/ways.json`, `data/jam_map/registries/*.json` | git (`main`) | при изменении |
| Пакеты журнала | `observations/YYYY-MM-DD/<sha256>.jsonl` | Releases, дневной архив | сегменты каждые 15 мин, архив после закрытия дня |
| Снимки событий | `snapshots/YYYY-MM-DD.jsonl` | Releases, дневной архив | то же |
| Карта пробок v2 | `jam_map/v2/YYYY-MM-DD.csv` | Releases, дневной архив | то же |

История git до внедрения Releases не переписана: старые копии архивных потоков
остаются в прошлых коммитах, из рабочего дерева они удаляются одним коммитом
после того, как всё локальное отгружено. Упакованный рост `.git` после этого
≈ 1 МБ/сутки вместо ≈ 12 МБ.

### Архивы в GitHub Releases

Дневной архив `traffic-YYYY-MM-DD.tar.xz` лежит в релизе `data-YYYY-MM`
(месяц дня) и содержит:

- `observations/<day>/<sha256>.jsonl` — пакеты журнала **распакованными**; имя —
  SHA-256 содержимого, день — UTC-дата первой строки пакета;
- `snapshots/<day>.jsonl` и `jam_map/v2/<day>.csv` — по алматинской дате;
- `MANIFEST.json` — SHA-256 и размер каждого члена, число строк, имена
  исходных сегментов, счётчики отброшенных дубликатов и обрезанных неполных
  строк, список разрывов (`gaps`), если данные части вахты были утеряны.

День D считается закрытым в `D+1 00:45 UTC`; до этого его данные лежат только
в сегментах `staging`. Внутри архива append-only файлы собираются из сегментов
разных вахт в порядке их старта; повторяющиеся строки и заголовки CSV
отбрасываются, поэтому переотгрузка одних байт безопасна. Prerelease `staging`
— внутренняя очередь: сборщик удаляет сегменты после консолидации, не
опирайтесь на него.

```bash
gh release download data-2026-09 --repo Dex719/almaty-traffic-data --pattern 'traffic-2026-09-16.tar.xz'
gh api repos/Dex719/almaty-traffic-data/releases/tags/data-2026-09 --jq '.assets[] | select(.name=="traffic-2026-09-16.tar.xz") | .digest'
sha256sum traffic-2026-09-16.tar.xz
tar -xJf traffic-2026-09-16.tar.xz
```

Оператору доступна ручная проверка и досборка:

```bash
GH_REPO=Dex719/almaty-traffic-data python -m collector.publish status --data-dir data
GH_REPO=Dex719/almaty-traffic-data python -m collector.publish consolidate --data-dir data
```

Внедрение: после merge текущая вахта дорабатывает на старом коде, преемник
стартует на новом; первая новая вахта консолидирует закрытые дни из чекаута,
отгружает открытый день сегментами и убирает архивные пути из индекса. После
этого добавьте `data/observations/`, `data/snapshots/`, `data/jam_map/v2/` в
`.gitignore` (раньше нельзя: старый код молча пропустил бы новые пакеты).

### Канонический журнал

`data/.state/journal.sqlite3` — SQLite/WAL, `synchronous=FULL`, одна транзакция
на наблюдение. Есть уникальный `observation_id`; повтор того же ID с другим
содержимым отклоняется. Сохраняются:

- `source`, `observed_at` с микросекундами и UTC offset, `source_ts`, `status`;
- код ошибки без полного ответа или секретных URL;
- полезная нагрузка, включая успешные части событий и качество карты.

Источник времени провайдера и время получения — разные поля. `tm` в URL тайла
не является временем обновления пробок. Время получения тайлов не доказывает,
что провайдер обновил их содержимое.

`data/observations/YYYY-MM-DD/<sha256>.jsonl.gz` — неизменяемые пакеты журнала
на диске сборщика. Состав пакета фиксируется в SQLite до записи файла. После
сбоя повторяется именно тот же пакет, даже если уже появились новые наблюдения.
Имя — SHA-256 **распакованного** JSONL. Повторы при объединении резервных копий
устраняйте по `observation_id`, не по минуте/баллу.

Экспорт каждые 15 минут и при штатной остановке. Успешный локальный экспорт
**не равен** внешней резервной копии. На Actions SQLite временный: только
отгруженные сегменты, дневные архивы или успешно загруженный recovery artifact
переживут удаление runner. При жёстком уничтожении runner последний интервал
(≤ 15 минут) может потеряться; для более строгого RPO используйте постоянный
сервер и внешний диск.

### Совместимые представления

- `data/scores/YYYY-MM.csv`: прежние столбцы; новые времена — полный ISO 8601.
  Строка отражает завершившуюся группу опросов, не гарантированную минутную сетку.
  Пустое поле не равно нулю. Нулевая длина пробок сохраняется как `0.0`.
  Счётчики событий записываются только при полном результате обоих слоёв.
- `data/events/YYYY-MM.json`: месячный реестр; ключ новых событий — `layer:id`.
  Существующий `first_seen` переносится из прошлого месяца или legacy-реестра.
  В git попадает не чаще раза в час; полная история событий — в журнале.
  `data/events.json` больше не пополняется и не удаляется.
- `snapshots/YYYY-MM-DD.jsonl` (в дневных архивах): уникальные ключи событий,
  `complete`, `layers`. Неполный снимок **нельзя** использовать для вывода,
  что событие исчезло.
- `jam_map/v2/YYYY-MM-DD.csv` (в дневных архивах): классы, версии
  реестра/алгоритма, количество тайлов, `quality`, доля распознанной длины
  внутри AOI для каждой геометрии.
- `data/jam_map/registries/<hash>.json`: неизменяемые версии геометрий.
  Порядок `classes` определяется исключительно соответствующей версией реестра.

Старые CSV/JSON и карта v1 сохраняются без массовой перезаписи. Эти файлы —
удобные представления, а не транзакционно связанная копия SQLite: после
аварии они могут отставать. Для восстановления полной ленты используйте журнал
и архивы наблюдений; не объявляйте полноту только по наличию CSV.

### География и ограничения измерений

AOI: `(43.165, 43.375, 76.72, 77.06)` = lat min/max, lon min/max.
События вне AOI **не удаляются**: поле `in_aoi` явно показывает попадание;
для ограничений проверяется пересечение сегментов с прямоугольником.
Совместимые общие счётчики продолжают описывать ответ источника целиком.
Для сравнения с картой агрегируйте только `in_aoi=true` из журнала событий.

Карта использует точки внутри AOI, взвешивание по длине и поиск соседних
пикселей через границы тайлов. Геометрия и проекции кэшируются по версии файла.
Загрузка ограничена четырьмя потоками, общим интервалом 0.2 с между стартами
запросов и бюджетом 120 с; недополученные тайлы запрашиваются повторно один раз
в пределах бюджета; незавершённые запросы дренируются с HTTP-таймаутами.
Это мягкий бюджет: патологически медленный поток ограничивает watchdog процесса.
Повреждённый PNG не уничтожает корректные тайлы, частичность не маскируется:
`quality=ok` — получены все тайлы, `partial` — часть, `low_coverage` — менее
50% распознанных геометрий с точками внутри AOI (консервативный сигнал
деградации, не оценка точности модели).

`G/Y/R/D` — категориальная оценка растрового слоя, **не скорость направленного
ребра**. `last_seen-first_seen` — окно наблюдения на карте, не точная длительность
ДТП. Направления движения и реальные времена поездок требуют дополнительной
калибровки. Смена цветовой схемы/контракта провайдера требует проверки человеком.

Публичный endpoint не означает неограниченную лицензию. Проверьте условия,
квоты и допустимость перепубликации. Тексты комментариев могут содержать личные
данные: определите политику публикации/удаления перед расширением аудитории.

## Развёртывание на постоянном сервере

Файлы конфигурации подготовлены, но сами ничего не устанавливают и не создают
платных ресурсов. Предполагаются `/opt/almaty-traffic-data` и пользователь `traffic`.

1. Клонируйте проверенную версию в `/opt/almaty-traffic-data`, создайте `.venv`,
   установите `requirements.txt`. Зависимости верхнего уровня закреплены;
   это не полный lock транзитивных зависимостей. Обновления приходят PR от Dependabot.
2. Создайте системного пользователя `traffic` и каталог
   `/var/lib/almaty-traffic/jam_map`, доступный ему на запись. Скопируйте туда
   `data/jam_map/ways.json`; старые исследовательские данные переносите отдельно.
3. Скопируйте `.env.example` в `/etc/almaty-traffic.env` с правами `0600`.
   При необходимости задайте `TRAFFIC_HEARTBEAT_URL` внешнего dead-man-switch.
   Сборщик отправляет сигнал только после сохранённых, здоровых результатов
   всех включённых источников; карта со статусом `partial` считается здоровой,
   если доля распознанных геометрий не ниже 95%. Рекомендуемый порог отсутствия
   сигнала — 5 минут.
4. Установите `deploy/almaty-traffic.service` в `/etc/systemd/system/`, затем:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now almaty-traffic.service
sudo journalctl -u almaty-traffic.service -f
```

Сервис запускается после перезагрузки. Watchdog перезапускает зависший процесс,
а не пытается «починить» недоступный источник. SIGTERM прекращает новые опросы,
дожидается активных задач и выполняет финальный экспорт. Нулевой сбор или ошибка
финального сохранения/публикации дают ненулевой код завершения.

Проверка состояния:

```bash
.venv/bin/python -m collector.ops check --data-dir /var/lib/almaty-traffic
```

Оповещение о выключенном сервере должно быть **внешним**: локальный health check
не может сообщить о собственном исчезновении. Health check контролирует минимум 100 МиБ свободного места. После настройки
внешнего backup включите `TRAFFIC_REQUIRE_BACKUP=1`: отсутствие проверенной
копии или возраст более 36 часов остановит heartbeat. Настройте также
мониторинг роста журнала и доступности внешнего хранилища.

## Резервные копии и восстановление

```bash
.venv/bin/python -m collector.ops export --data-dir /var/lib/almaty-traffic
.venv/bin/python -m collector.ops backup --data-dir /var/lib/almaty-traffic --destination /mnt/traffic-backups
```

Backup использует SQLite backup API и `integrity_check`, сохраняет gzip и
SHA-256 manifest. Подключите **внешнюю** файловую систему в `/mnt/traffic-backups`,
предоставьте пользователю `traffic` права записи и установите backup service/timer
из `deploy/`. Без mount point задание не запускается. Daily timer допускает
потерю до суток при потере основного диска: для меньшего RPO настройте частоту
и копирование пакетов наружу. Автоматическая загрузка в S3 без ваших настроек
учётных данных/назначения не включается.

Backup копирует версии `jam_map/registries/` с проверкой hash; храните также
конфигурацию и проверенную версию кода.
Проверяйте успешность таймера, checksum и восстановление на отдельном каталоге.
Политика retention намеренно не удаляет накопленные данные автоматически.

Для восстановления: остановите сервис, проверьте SHA-256 gzip по manifest,
распакуйте snapshot в **новый** каталог `.state/journal.sqlite3`, выполните
`PRAGMA integrity_check`, восстановите реестры геометрий и права, затем запустите
экспорт/коллектор с этим каталогом. Не копируйте один живой `.sqlite3` без WAL.

Откат к v1: остановите новый сборщик, сохраните журнал/архивы/геометрии, верните
предыдущую версию кода. V1 не понимает журнал v2 и не должен писать поверх него.
Откат публикации через Releases: вернуть предыдущую версию кода; дневные архивы
остаются в Releases, сегменты `staging` можно дособорать вручную
(`python -m collector.publish consolidate`). Исторические файлы в git не менялись.

## Проверки и безопасность

Тесты проверяют миграцию, нули, координаты, независимость слоёв, частичные
снимки, соседние тайлы, повтор тайлов, кэш, идемпотентность, сбой между экспортом
и ack, backup/restore, process lock, здоровье, публикацию в Releases с фейковым
клиентом (сегменты, сборка дня из нескольких вахт, разрывы, cleanup) и Git с
настоящим локальным remote. CI выполняет их с реальными зависимостями на
Python 3.12/3.13, без опроса провайдеров и без обращений к GitHub API.

Никогда не вставляйте PAT в исходники, remote URL, логи или PR. Подключения и
секреты настраиваются отдельно; сборщик берёт токен только из `GH_TOKEN` и
вырезает токены из сообщений об ошибках. Токен, опубликованный в чате, следует
отозвать. Recovery artifacts и дневные архивы содержат комментарии водителей и
полный журнал: ограничьте доступ и учитывайте срок хранения. Они не заменяют
независимую резервную копию.
