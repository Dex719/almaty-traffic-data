# Requirements: release-archive-publishing

**Spec Type:** Feature Spec (Requirements → Design → Tasks)
**Created:** 2026-09-17 · **Owner:** Dex719 · **Status:** Implemented, awaiting merge (PR) → post-cutover TSK-013

## Контекст и проблема

Сборщик публикует все данные в `main` каждые 15 минут. Упакованный рост `.git`
измерен по последним 300 коммитам (≈3.1 суток):

| Поток | Рост `.git`, МБ/сутки | Причина |
|---|---|---|
| `data/observations/**` (батчи `.jsonl.gz`) | ≈ 7.5 | gzip не дельтируется, каждый батч хранится целиком |
| `data/events/YYYY-MM.json` (9 МБ, перезапись каждые 5 мин) | ≈ 2.8 | `last_seen` меняется у ~1000 событий в каждом коммите |
| `data/jam_map/v2/*.csv` (30 КБ строка каждые 5 мин) | ≈ 1.1 | текст, дельты |
| `data/snapshots/**` | ≈ 0.8 | текст, дельты |
| `data/scores/*.csv` | ≈ 0.35 | append |
| **Итого** | **≈ 12.5** | ≈ 4.5 ГБ/год; `.git` уже 128 МБ за 16 дней |

Рабочее дерево прибавляет ≈ 20 МБ/сутки. Через 3–4 месяца репозиторий превысит
рекомендуемый GitHub 1 ГБ; checkout каждой вахты и `pull --rebase` будут замедляться.

**Цель:** git хранит только компактные live-представления; тяжёлые потоки уходят
в GitHub Releases без ухудшения RPO (сейчас ≤ 15 мин) и без переписывания истории.

## Роли

- **Оператор** (владелец репозитория): запускает workflow, читает Actions и Releases.
- **Потребитель данных** (krisha-fair-price / аналитики): читает live-представления из git и дневные архивы из Releases. Прямых ссылок на файлы этого репозитория в krisha-fair-price нет (проверено grep).
- **Сборщик**: процесс `python -m collector.shift --git` на GitHub Actions (единственный писатель, `concurrency` группа).

## Глоссарий

- **Архивные потоки**: `data/observations/**`, `data/snapshots/**`, `data/jam_map/v2/**`.
- **Live-представления**: `data/scores/*.csv`, `data/events/*.json`, `data/jam_map/ways.json`, `data/jam_map/registries/*.json`.
- **Сегмент**: неизменяемый `tar.xz` с приращением архивных потоков с прошлой отгрузки; актив релиза `staging` с именем `seg-<UTC>-<run_id>-<seq>-<days>.tar.xz`.
- **Дневной архив**: `traffic-YYYY-MM-DD.tar.xz` в месячном релизе `data-YYYY-MM` (месяц дня D).
- **День D**: календарная дата в пути файла (observations — UTC-дата первой строки батча; snapshots и jam_map — алматинская дата). Архив дня D объединяет файлы всех трёх потоков с датой D в пути.
- **Закрытие дня D**: `now_utc ≥ D+1 00:45 UTC` (последний батч UTC-дня экспортируется не позднее D+1 00:15 UTC с запасом на задержки цикла).
- **Отгружено (shipped)**: байты, вошедшие в сегмент, загрузка которого подтверждена sha256-digest API.
- **Консолидировано**: дневной архив присутствует в месячном релизе с подтверждённым digest.

## Функциональные требования

### FR-1 Разделение потоков публикации (Must)
- WHEN сборщик публикует с `--git`, the system SHALL добавлять в git-коммит только live-представления.
- WHEN формируется git-коммит, the system SHALL NOT добавлять файлы архивных потоков.
- IF путь live-представления отсутствует на диске, THEN the system SHALL пропустить его без ошибки.
- **AC-1.1** Given каталог `data` с новыми файлами всех потоков, When выполняется публикация, Then коммит содержит только пути live-представлений.
- **AC-1.2** Given отсутствует `data/events`, When выполняется публикация, Then `git add` не завершается ошибкой.

### FR-2 Отгрузка сегментов (Must)
- WHEN завершился экспортный цикл (15 мин) или штатная остановка AND есть неотгруженные данные архивных потоков, the system SHALL загрузить один сегмент в релиз `staging`.
- WHEN API подтверждает актив с sha256, равным локальному, the system SHALL продвинуть отгруженные смещения и сохранить их в `data/.state/publish.json`.
- IF подтверждение не получено, THEN the system SHALL оставить смещения без изменений и включить те же данные в следующий сегмент.
- WHEN неотгруженных данных нет, the system SHALL NOT создавать сегмент.
- IF релиз `staging` отсутствует, THEN the system SHALL создать его как prerelease.
- WHEN объём неотгруженных данных превышает 64 МиБ, the system SHALL отгрузить старейшие файлы в пределах лимита, остальное — в следующих циклах.
- WHEN день файла уже консолидирован, the system SHALL NOT отгружать его.
- IF актив с именем сегмента уже существует в незавершённом состоянии (`state ≠ uploaded`) или с другим размером, THEN the system SHALL удалить его перед загрузкой.
- **AC-2.1** Given два новых батча и 300 дописанных байт в `jam_map/v2/D.csv`, When `ship`, Then один актив; manifest содержит 3 записи с `offset/length/sha256`; состояние продвинуто.
- **AC-2.2** Given API возвращает неверный digest, When `ship`, Then результат `False`, состояние не изменилось, следующий `ship` включает те же байты.
- **AC-2.3** Given нечего отгружать, When `ship`, Then загрузок нет, результат `True`.
- **AC-2.4** Given процесс перезапущен с сохранённым `publish.json` того же run, When `ship`, Then ранее отгруженные байты не отгружаются повторно.

### FR-3 Консолидация дня (Must)
- WHEN день D закрыт AND у D есть данные (локально или в `staging`) AND в релизе `data-<месяц D>` нет `traffic-D.tar.xz`, the system SHALL собрать дневной архив и загрузить его с проверкой sha256.
- WHEN собирается дневной архив, the system SHALL включить батчи observations распакованными как `observations/D/<digest>.jsonl`, файлы `snapshots/D.jsonl`, `jam_map/v2/D.csv` и `MANIFEST.json` (sha256 и размер каждого члена, число строк, источники сегментов, разрывы).
- WHEN собираются append-only файлы, the system SHALL упорядочить сегменты по времени старта run, внутри run — по `offset`, отбрасывать повторяющиеся строки (первое вхождение сохраняется) и повторные заголовки CSV.
- WHEN у текущего run есть локальные файлы дня D, the system SHALL использовать их вместо его же сегментов из `staging`.
- IF обнаружен разрыв смещений внутри run, THEN the system SHALL собрать архив из имеющихся данных и перечислить разрывы в `MANIFEST.json`.
- WHEN день консолидирован, the system SHALL удалить из `staging` сегменты, все дни которых консолидированы.
- IF консолидация завершилась ошибкой, THEN the system SHALL продолжить сбор, залогировать ошибку без секретов и повторить попытку в следующем цикле или вахте.
- IF месячный релиз отсутствует, THEN the system SHALL создать его с тегом `data-YYYY-MM` и описанием формата.
- WHEN консолидация выполняется, the system SHALL NOT блокировать цикл опроса источников и watchdog.
- **AC-3.1** Given сегменты run A и run B за день D и локальные файлы текущего run C, When `consolidate`, Then строки идут в порядке A → B → C без дубликатов, батчи распакованы, `MANIFEST.json` содержит sha256 каждого члена, актив загружен и подтверждён.
- **AC-3.2** Given день D закрыт и `traffic-D.tar.xz` уже есть, When `consolidate`, Then загрузок нет.
- **AC-3.3** Given день D не закрыт, When `consolidate`, Then D пропущен.
- **AC-3.4** Given после консолидации D в `staging` есть сегмент с днями {D, D+1} и сегмент с днями {D}, When cleanup, Then первый сохранён, второй удалён.
- **AC-3.5** Given API загрузки падает, When `consolidate`, Then исключение не покидает фоновую задачу, следующий вызов повторяет попытку.

### FR-4 Миграция git-дерева без переписывания истории (Must)
- WHEN все локальные данные архивных потоков отгружены или консолидированы (backlog = 0), the system SHALL удалить архивные потоки из индекса git (`git rm --cached`, файлы остаются на диске) в ближайшем коммите публикации.
- The system SHALL NOT переписывать историю git.
- WHEN прежняя вахта (старый код) работает параллельно с внедрением, the system SHALL NOT терять её данные: `.gitignore` для архивных потоков в этом изменении не добавляется (иначе старый код молча пропустит новые батчи).
- **AC-4.1** Given архивные файлы в индексе и backlog = 0, When `commit_and_push(drop_archive=True)`, Then файлы удалены из индекса, но существуют на диске, коммит запушен.
- **AC-4.2** Given backlog > 0, When публикация, Then архивные файлы остаются в индексе.

### FR-5 Частота публикации реестра событий (Should)
- WHEN выполняется публикация, the system SHALL добавлять `data/events/` в коммит не чаще одного раза в 60 минут; остальные live-представления — каждый цикл.
- WHEN в рабочем дереве есть незастейдженные изменения tracked-файлов, the system SHALL выполнять `pull --rebase --autostash`.
- WHEN вахта завершается, the system SHALL включить `data/events/` в финальный коммит независимо от таймера.
- **AC-5.1** Given `include_events=False`, When публикация, Then `data/events` в коммите отсутствует, остальные live-пути присутствуют.
- **AC-5.2** Given изменённый tracked-файл вне индекса, When `pull --rebase`, Then публикация успешна.

### FR-6 Документация и доступ потребителя (Must)
- WHEN README описывает данные, the system SHALL указывать, что лежит в git, что в Releases, как скачать (`gh release download`) и проверить архив (`MANIFEST.json` + digest API), а также правило закрытия дня.

### FR-7 CLI оператора (Should)
- WHEN оператор запускает `python -m collector.publish {status|ship|consolidate} --data-dir <dir>`, the system SHALL выполнить действие с `GH_TOKEN`/`GH_REPO` из окружения и вернуть ненулевой код при ошибке.

### FR-8 Серверный режим без изменений (Must)
- WHEN сборщик запущен без `--git`, the system SHALL NOT обращаться к GitHub и SHALL NOT требовать `gh`.

## Нефункциональные требования

- **NFR-1 Рост**: упакованный рост `.git` ≤ 1.5 МБ/сутки после внедрения (сейчас ≈ 12.5).
- **NFR-2 RPO** ≤ 15 минут: сегменты отгружаются в каждом экспортном цикле и при остановке.
- **NFR-3 Бюджеты**: отгрузка сегмента ≤ 120 с на цикл (таймауты `gh`); консолидация — в фоновом daemon-потоке; при остановке сначала финальная отгрузка и push, затем процесс завершается, не дожидаясь консолидации.
- **NFR-4 Безопасность**: токен только из `GH_TOKEN`; не логируется; сообщения об ошибках не содержат URL с секретами; права workflow — `contents: write` (достаточно для Releases).
- **NFR-5 Идемпотентность**: повторный запуск любого шага не дублирует активы и не портит архивы.
- **NFR-6 Тесты офлайн**: фейковая реализация клиента Releases; CI без обращений к GitHub.

## Edge cases

- Сегмент, пересекающий полночь: содержит файлы двух дней; имя перечисляет оба; удаляется только когда оба консолидированы.
- Runner уничтожен до отгрузки: теряется ≤ 15 мин (как сейчас, документировано).
- Первая вахта на новом коде: чекаут содержит архивные файлы из git за 11 дней; закрытые дни консолидируются из локальных файлов, открытый день отгружается сегментами; затем пути удаляются из индекса.
- Прежняя вахта параллельно дописывает архивные потоки в git до своего конца: новая вахта видит их в чекауте как локальные файлы и обрабатывает как выше.
- Повторная отгрузка одних байт под разными run (например, вахта умерла до `git rm --cached`): построчная дедупликация при сборке.
- `gh` отсутствует или `GH_TOKEN` пуст: отгрузка не удаётся → семантика как при неудачном push (стагнация 45 мин → код 1, recovery artifact).
- 429/5xx GitHub: попытка не засчитывается, повтор в следующем цикле.
- Актив в состоянии `starter` после оборванной загрузки: удаляется перед повторной загрузкой.

## Ограничения

- `gh` CLI на `ubuntu-latest`; Python 3.12 stdlib (`lzma`, `tarfile`, `json`).
- Актив ≤ 2 ГБ; имя актива уникально внутри релиза; имя ≤ 200 символов.
- Один писатель благодаря `concurrency: traffic-collector`.

## Out of scope

- Переписывание истории git и уменьшение уже накопленных 128 МБ (отдельное решение оператора).
- Git LFS.
- Отгрузка в Releases с постоянного сервера (там есть диск и backup timer).
- Пересборка snapshots и jam_map из журнала.
