**Spec Type:** Bugfix Spec (bugfix + tasks одним проходом: причины найдены и воспроизведены, запуск оператором «чини и фикси баги») · **Created:** 2026-09-23 · **Status:** Done: BUG-1..5 fixed (PR #11), восстановление 2026-09-17/18 выполнено 2026-09-24, проверено на проде 2026-09-25 (TSK-B09)
**Источник:** ревью Actions и Releases 2026-09-23: консолидация 2026-09-17 и 2026-09-18 падает каждые 15 минут начиная с 2026-09-18 00:45 UTC.
**Связь:** уточняет FR-2, FR-3, FR-7 и edge case «starter» спеки [release-archive-publishing](../release-archive-publishing/requirements.md).

## BUG-1 Оборванная загрузка сегмента навсегда блокирует консолидацию его дней

- **Current behavior:** 2026-09-17 20:07 UTC `gh release upload` сегмента `seg-20260917T200731Z-35243010838-0015-2026-09-17+2026-09-18.tar.xz` (66 588 байт) прерван таймаутом 120 с. Актив остался в состоянии `starter` (id 571001306). `Consolidator.staging_segments()` берёт имена из `GET /releases/{id}/assets`, где такой актив есть, и не фильтрует по `state`. `gh release download --pattern` ищет по объекту релиза, а там его нет → `no assets match the file pattern` → сборка дня падает. Сегмент покрывает два дня, поэтому 2026-09-17 и 2026-09-18 не консолидируются шестые сутки. `cleanup_staging` не удаляет ~150 сегментов этих дней, а каждый проход впустую скачивает ~40 сегментов (оценка 250–600 вызовов API в час при лимите `GITHUB_TOKEN` 1000 в час). Штатно удалить актив тоже нельзя: `gh release delete-asset` ищет по тому же объекту релиза.
- **Expected behavior:** консолидация и `known_days` учитывают только активы `state == "uploaded"`. Данные оборванной загрузки `Shipper` перезаливает следующим сегментом, потому что смещения двигаются только после подтверждённого digest. `cleanup_staging` удаляет незавершённые активы `staging` старше 1 часа по id через REST (`DELETE /repos/{owner}/{repo}/releases/assets/{id}`). Более молодые не трогает: загрузка может идти прямо сейчас. Ошибка удаления одного актива логируется и не останавливает очистку остальных.
- **Unchanged behavior:** формат и имена сегментов; порядок сборки и дедупликация; сегмент удаляется только когда консолидированы все его дни; `is_consolidated` по-прежнему требует `uploaded`.
- **Root cause:** реализация FR-2 держалась на двух неверных допущениях. Первое: повтор загрузки идёт под тем же именем, хотя имя сегмента содержит метку времени и повтор всегда получает новое. Второе: `gh` умеет удалять `starter`, хотя он его не видит (`pkg/cmd/release/download/download.go:212`, `pkg/cmd/release/delete-asset/delete_asset.go:97` в cli/cli). Фильтр состояния в FR-3 не требовался. `FakeReleases` в тестах всегда отдавал `uploaded`, поэтому тесты разницу не ловили.
- **Regressions to check:** все `ConsolidatorTests`, включая `test_midnight_segment_survives_until_both_days_consolidated`; новые `test_interrupted_segment_upload_does_not_block_consolidation`, `test_orphaned_upload_deleted_only_after_grace_period`, `test_cleanup_continues_after_failed_deletion`.

## BUG-2 Оборванная загрузка дневного архива заблокирует день навсегда (латентный)

- **Current behavior:** если прервётся загрузка `traffic-D.tar.xz`, следующий проход найдёт `starter`-актив с тем же именем. `upload_verified` вызовет `gh release delete-asset` и получит «not found» → консолидация D будет падать на каждом проходе. То же при удалении актива с несовпавшим digest.
- **Expected behavior:** `upload_verified` удаляет существующий или неверный актив по id через REST и загружает заново.
- **Unchanged behavior:** совпадающий `uploaded`-актив засчитывается без загрузки; верификация digest и size.
- **Root cause:** удаление по имени через `gh release delete-asset`.
- **Regressions to check:** `test_upload_failure_is_contained_and_retried`; новый `test_stale_daily_archive_in_starter_state_is_replaced`; `GhClientTests` с командой `gh api -X DELETE repos/{owner}/{repo}/releases/assets/<id>`.

## BUG-3 Отгрузка поздних данных за уже собранный день теряет их молча

- **Current behavior:** README после отмены вахты предписывает отгрузить хвост из артефакта `python -m collector.publish ship`. Если день уже консолидирован (закрывается в D+1 00:45 UTC, преемник собирает его сам), CLI всё равно отгружает сегмент: множество `consolidated` в CLI пустое. Следующий `cleanup_staging` удаляет сегмент как «все дни консолидированы». Байты в архив не попадают, CLI выходит с кодом 0.
- **Expected behavior:** `ship` сначала определяет уже консолидированные дни и не отгружает их файлы. Он печатает `refused_days`, в лог ERROR пишет «сохраните каталог» и завершается кодом 1. Остальные дни отгружаются как раньше.
- **Unchanged behavior:** неизменяемость дневных архивов (слияние поздних данных в готовый архив вне объёма). Поведение вахты тоже прежнее: `pending()` пропускает консолидированные дни, потому что байты этого run уже вошли в архив из его локальных файлов.
- **Root cause:** проверку «день консолидирован» выполняет только фоновый консолидатор вахты, CLI её не делает.
- **Regressions to check:** новый `test_cli_ship_refuses_days_already_archived`; все `ShipperTests`.

## BUG-4 Застрявший день никто не видит

- **Current behavior:** ошибка консолидации пишется в лог ERROR каждые 15 минут, run завершается успешно, аннотаций нет. Поломку 2026-09-17/18 никто не замечал 6 суток.
- **Expected behavior:** если закрытый день не консолидирован через 24 часа после закрытия, консолидатор один раз за процесс на каждый день пишет ERROR. Под GitHub Actions (`GITHUB_ACTIONS=true`) он печатает `::error::`, и на странице run появляется аннотация.
- **Unchanged behavior:** консолидация не прерывает сбор; код выхода вахты не меняется.
- **Root cause:** нет эскалации устойчивой ошибки фоновой задачи.
- **Regressions to check:** новый `test_stuck_day_is_annotated_once`.

## BUG-5 `--run-id` с дефисом создаёт сегмент, который консолидатор не распознаёт

- **Current behavior:** `default_run_id()` нормализует идентификатор, а `--run-id` в CLI нет. `seg-...-recovery-1-0000-...` не проходит `SEGMENT_RE`, поэтому такой сегмент никогда не консолидируется и не удаляется.
- **Expected behavior:** CLI отклоняет `--run-id` вне `[A-Za-z0-9_]+` (ошибка argparse, код 2); `Shipper` проверяет run_id и бросает `ValueError`.
- **Unchanged behavior:** `default_run_id()`; документированный `recovery_<run_id>`.
- **Root cause:** нет проверки пользовательского ввода, который становится частью имени актива.
- **Regressions to check:** новый `test_cli_rejects_run_id_that_breaks_segment_names`.

## Разовое восстановление 2026-09-17/18 (оператор)

Если просто удалить `starter`-актив, вахта на старом коде сама бросится догонять: ~170 скачиваний и ~150 удалений за один проход при лимите `GITHUB_TOKEN` 1000 вызовов в час. Поэтому восстановление выполняется с машины оператора, на личном лимите (5000 в час). Для этого достаточно исправленного CLI из ветки фикса, запущенного на пустом каталоге:

```bash
GH_REPO=Dex719/almaty-traffic-data python -m collector.publish consolidate --data-dir <пустой каталог> --run-id hotfix_20260923
```

1. `staging_segments` пропускает `starter`, поэтому дни 17 и 18 собираются из подтверждённых сегментов и заливаются в `data-2026-09`. Пока это идёт, `starter` остаётся на месте, и вахта на старом коде спотыкается о него, как раньше, а сама догонять не начинает.
2. Затем `cleanup_staging` по id удаляет сегменты собранных дней и сам `starter` (ему больше `ORPHAN_AGE`).
3. Проверить: оба архива `uploaded` с digest, в `staging` нет незавершённых активов и сегментов 17–18 сентября.

Данные не теряются: сегмент с тем же `seq 0015` в 20:22 (id 571038964, 125 036 байт) содержит байты оборванного.

**Порядок раскатки:** сначала восстановление, потом merge. Если влить фикс раньше, первая вахта на новом коде сама догонит 17–18 сентября на токене Actions. По оценке, это ~500–650 вызовов API за один проход: ~170 скачиваний по 2–3 вызова и ~150 удалений по одному вызову по id. В тот же часовой лимит попадают и вызовы предыдущей вахты, так что оставшегося запаса может не хватить.

## Не в объёме

- Слияние поздних данных в готовый дневной архив (новая версия или дополнительный актив): меняет контракт неизменяемости, нужна отдельная спека.
- Скачивание сегментов по id через REST (экономия ~2 вызовов API на сегмент): оптимизация, поведение не меняет.
- `runs-on: ubuntu-24.04`, PR Dependabot, кэш реестра событий в `store.py`: отдельные задачи.
